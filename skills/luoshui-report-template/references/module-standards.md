# 洛水研报模版 · 模块级版式统一标准

> 原则：**版式与数据分离** —— 改数据只改 JSON，改样式只改生成器 + CSS 文件，
> **不手写模块 HTML、不直接改产物**。
>
> 本文件＝**各模块（m1–m31）的版式标准**。同目录另有三份按场景拆开的文档：
> `chart-specs.md`（**图表**专项）· `frontend-style.md`（**样式 / 表格 / 页面**）·
> `hard-rules.md`（要求清单）· `pipeline.md`（流程）· `deploy-verify.md`（部署验收）

## 8. 模块 25「产量储量分布及价格分析」= 地图必配（2026-10-14 用户令 · 锁死）


用户口径：「还有一块也要锁死，模块 25 产量储量分布及价格分析，这个里面的**世界地图和中国地图**
的分布图**必须每份研报都要**，有储量比如矿企的**储量和产量分布图都要**，没有储量的比如
化工或者农产品企业**就用产量分布图**」

### 8.1 硬性矩阵（★ 地图不再是"可选块"）

| 企业类型 | 世界图（`world_map`） | 中国图（`cn_map`） | 产量维度 |
|---|---|---|---|
| **有储量**（矿企） | **储量**分布 | **储量**分省 | 另配**产量分布**：`chartResDist`（储量 vs 产量 双轴）或独立产量图 / 表 |
| **无储量**（化工 / 农产品） | **产量（产能）**分布 | **产量（产能）**分省 | 就是上面这两张地图 |

- **世界地图 + 中国地图 = 每份研报必配的两张**（底线，不可省）
- 矿企：**储量维度走地图、产量维度走对比图表**（母本 600456 就是这么做的）
- 化工 / 农产品：**换主题而不是省掉** —— 两张地图画「产量 / 产能的地理分布」
- ⚠️ 旧注释「化肥 / 化工的产能分布不是地理分布，不要硬套地图」**已作废**
  （那是没数据时的推脱）；正确做法是取**按国家 / 按省的真实产量或产能**，这就是地理分布。

### 8.2 母本参照（宝钛 600456，5 张图，最全形态）

| 图槽 | 名称 | 类型 |
|---|---|---|
| `chartTiWorldMap` | 全球钛铁矿**储量**分布（2023，万吨） | map（world） |
| `chartTiShare` | 各国**储量占比 vs 产量占比**（2023） | bar ← 产量维度 |
| `chartTiCNMap` | 中国原生钛铁矿**储量**分布（2022） | map（china） |
| `chartTiCNProv` | 中国原生钛铁矿**储量分省**（2022） | bar |
| `chartTiPrice` | 攀枝花钛矿价格走势（2024-09 ~ 2026-09） | line |

**段落顺序**：世界储量图 → 表格 → 储量/产量对比 → 中国分省图 → 分省表 → 价格图。

### 8.3 唯一通道（**不改模板、不改 HTML**）

地图由 `report_build_v31.py::m_res()` ＋ `res_map_charts()` 自动产出 ——
**只要在 `data_v31_<code>.json` 的 `resource` 块里给数据**：

```json
"resource": {
  "world_map": {
    "slot": "chartXxxWorldMap",        // 图槽名（自定义；须与 m_res 里引用的名字一致）
    "label": "铂族金属（PGM）储量",      // tooltip 指标名（换矿种不用改壳）
    "unit": "吨",
    "total": 76200,                    // 占比分母；不给 ⇒ 用各值之和
    "total_word": "占全球",
    "nodata": "USGS 2025 年统计未单独列示",
    "values": [["South Africa", "南非", 63000], ...],   // 英文名 / 中文名 / 值
    "tiers": [[20000, "#a30f24"], [5000, "#d0202f"], [500, "#e06670"], [0, "#eea3aa"]],
    "pos":    {"Zimbabwe": "right"},   // 可选：标签朝向覆盖（默认表上增量）
    "small":  [...], "no_label": [...],// 可选：字号 / 完全关标签（**必须按本次数据重定**）
    "note":   "口径说明"
  },
  "cn_map": { "...同上，values 用省简称...",
              "head": [...], "rows": [...], "table_note": "...", "reading": "这张图最该注意的一件事" },
  "rows": [], "head": [], "axis_names": ["储量", "产量"],   // chartResDist 用
  "price_rows": [], "price_head": [], "price_unit": ""      // chartResPrice 用
}
```

然后 `python3 report_build_v31.py <code>` 就会把两张地图带出来（无需改任何模板）。

### 8.4 坑（`chartmap.py::selfcheck()` 已逐条断言；改前必读 `build/README_地图批量出图.md`）

1. ★★ **底图合规（最高优先）**：世界图必须用**国标版** `build/lib/world-cn.js`
   （`registerMap('worldcn')`）。ECharts 官方 world 图**台湾未并入中国版图、藏南被划给印度、
   缺南海诸岛与九段线** —— **研报里出现这种地图是不可接受的**。
   **判定标准是"画法"，不是"哪一家"**：台湾 / 藏南 / 港澳 / 九段线画对 ✔ 即达标。
   当前实现用阿里 DataV `areas_v3`（`100000_full`），**上游是「高德开放平台」**。
   ⚠️ DataV 的官方授权口径是「**仅供学习交流使用，不得用于商业目的**」，且数据版本停在 2021.5
   ⇒ **内部研究 / 示意用途可用**；一旦要**商用或正式对外发布**，应换成
   **高德开放平台授权数据** / **天地图**（国家地理信息公共服务平台）/
   **自然资源部标准地图**（带审图号）。换源时**只需保证画法仍是国标**，覆盖层接口不变。
   ⚠️ 中国图的 `name` 用**省简称**，其中 `台湾` / `中国香港` / `中国澳门` 也是简称形式。
   ★ **2026-10-14 已逐项实测通过**（用 `build/check_map_compliance.py` 复跑，不看注释只看几何）：
     台湾 ✓ · 藏南 7 采样点全属 China **且 India 已不再伸入** ✓ · 港澳 ✓ ·
     九段线 9 段 ✓ · 阿克赛钦 ✓ · 分省底图含「南海诸岛」单元 ✓
   ★ **India 的几何已裁干净**：原数据里 India 仍覆盖藏南（lon 91~97，最北到 lat 28.12），
     过去靠「China 挪到 features 末尾、后绘制压住」兜底 —— 视觉对、**数据不干净**。
     `build/fix_map_india_overlap.py` 已用几何差集（India − China，重叠 0.60 平方度 = 0.23%）
     裁掉；**改完必须重新发 `report.html`**（地图是内联在页面里的）。
2. `series.map` 同时给 `geoIndex` ⇒ 区域填充权交给 geo，`data[].areaColor` **被整体忽略、全图变灰**
   （更坑的是 `getOption()` 还会正确回显 ⇒ 探针读"对"了、画面是灰的）。
3. 标签另起 `scatter` + 独立 `geo` 锚点 ⇒ **一放大就错位**（两套坐标系）。
4. map 的 `{c}` **不走** `valueFormatter`；富文本 tooltip 只能走壳里的 `FNS.mapTip` / `mapCnTip` 令牌
   ⇒ **改令牌协议必须同步重编并上传壳（`report.html`）**，否则新图在线上仍按旧口径显示。
5. `tiers` 分档阈值必须按**本次数据**的实际分布定，照抄别的矿种会让所有区域塌进同一档（一片同色）；
   `selfcheck()` 断言「至少用到 2 档」。
6. `no_label` / `small` 必须按本次数据**重定** —— 母本默认为钛铁矿的地理调过，直接继承会
   **把最大的那个省关掉标签**（贵研甘肃占全国 69.6%、恒邦甘肃储量全国第二，都会被关）。
7. 分母 `total` 与 `values` 之和**允许不等**（世界图常有「其他国家和地区」），
   但要写进 `note` 说清口径，否则占比看着像算错了。

## 9. ★★ 数据块的「形状契约」：填错形状 = 版式崩掉（2026-10-15 西藏矿业血泪）


**这一节是整个 skill 里最容易踩、后果最直接的一节。**
`report_build_v31.py` 的渲染器**不校验数据块形状** —— 你把段落填进一个期望二维数组的字段，
它照样 `table(head, 该字段)` 渲染，**结果是几千像素宽的破表**（容器只有 ~1,058px）。

### 9.1 「收表行」的字段 vs 「收段落」的字段

| 字段 | 期望形状 | 填错的后果 |
|---|---|---|
| `raw.rows` / `raw.balance` | **二维数组**（每行元素数 == `head` 列数） | 段落 → 5 列巨宽表 |
| `cashflow.flows` | **二维数组** | 段落 → 9 列巨宽表 |
| `capacity.rows` / `production.rows` / `pricecost.rows` / `bizmix.rows` / `raw.rows` | 二维数组 | 同上 |
| `peers.rows` / `sdbalance.*_rows` / `industry.rows` / `demand.rows` / `resource.rows` | 二维数组 | 同上 |
| `risk.rows` / `peers.rows` / `conclusion.todo` / `conclusion.watch` | 二维数组（3 列） | 列数对不上 → 串列 |
| `cashflow.note` / `raw.note` / `raw.transmit` / `bizmix.note` / `volprice.note` | **字符串**（走 `logic()` 折叠块） | 传数组会拼出乱码 |
| `conclusion.triggers` | **字符串 list**（走 `ul()`） | 传二维数组会渲染成表格套表格 |
| `risk.events` / `bullbear.bull` / `bullbear.bear` | 二维数组 | — |

> **一句话记法**：**要进 `<table>` 的字段收数组，要进折叠解读块的字段收字符串。**
> 段落的唯一去处是 `note` / `transmit` / `logic` / `deep`，**永远不要塞进 `rows` / `flows` / `balance`**。

### 9.2 ★ `wb_report_charts` 的行**删不掉** —— 图槽数据填错了怎么办

- `wb_report_charts` **没有 `is_del` 列**；`wb_admin_delete_row` 的 `p_kind` 白名单里
  也**没有 charts**（只有 tasks/permits/milestones/watch/contacts/logs/works）。
- ⇒ **一旦把错的图数据推上库，那一行就永久留在库里了**（`push_reports_v31.py` 只 upsert，
  不会删多余的），下次再推会一直报「图表 N/N（集合一致：否）」。

**正确处置顺序（西藏矿业踩过）**：
1. 先看这个图槽**在业务上到底有没有意义**；
2. **有** ⇒ 换成**真的**序列（西藏矿业：`chartRaw` 原本被我误填成资本开支
   `[13.68, 7.72, 0.23]`，而公司资源自给 100% 根本没有外购原料 ——
   最后改成**进口铬矿石价格**，因为它是自有铬矿的售价天花板，28 个月末观测点）；
3. **确实没有** ⇒ 让渲染器**不引用**它（`raw.numeric` 不给 ⇒ 渲染器不出图槽），
   **但库里那一行仍然要留着**，且推库时用**完整的图集合**去覆盖，保证下次一致。

### 9.3 ★ 三处「形状特别」的块（写错就 AttributeError）

| 字段 | 形状 | 备注 |
|---|---|---|
| `controller` | `{'gaps': {'title','head','rows','note'}, 'deep': [...]}` | **`gaps` 是 dict 不是 list** —— 传 list 直接 `AttributeError: 'list' object has no attribute 'get'` |
| `score` | `{'h1': {...}, 'kpi': {...}, 'notes': [10 条字符串], 'scores': None}` | **`h1`/`kpi` 是 dict，`notes` 是 list** —— 反了就是同样的 AttributeError |
| `conclusion` | `{'verdict': 字符串, 'todo': 3 列, 'triggers': [字符串], 'watch': 3 列}` | 列数与 `m31` 的表头硬绑定 |

### 9.4 验收：一定要量「卡片横向溢出」

`card-overflow` 是**唯一能提前抓到形状错误**的指标 —— 它在形状填错时会立刻 > 0
（西藏矿业 000762 修之前：`m15 sw=1351 / m23 sw=10886 / cw=1058`；修之后：`NONE`）。
`probe_report_mac.py` 已内置该项；**新报告必须 `card-overflow=0` 才算过**。

### 9.5 ★★ 喂图的数据块：**优先用专用键，别靠列号硬取**（2026-10-16 西藏矿业）

**最贵的教训先说**：**「画错的图」比「空白的图」危险得多。** 空白图一眼能看出不对；
而列义错位的图**照常渲染、图例齐全、不报错**。000762 线上就挂着两张这样的图：

| 图 | 原来实际画的是什么 | 真相 |
|---|---|---|
| m7 `chartProd` | 三条系列读**列 1/2/3** | 而该表列义是「2025 产量 / 2026H1 产量 / 2026H1 销量」⇒ **把 2026H1 产量当销量、把销量当产销率** |
| m11 `chartMix` | 「毛利率」折线读 `bizmix.rows` 的**列 3** | 新口径下**列 3 是「收入（万元）」** ⇒ 把 6748 万元当 6748% 画 |

**根因**：`rows` 是给人看的表，列义**随 `head` 变**；图却按写死的列号取数。

**① 有专用键就用专用键。** 渲染器已按此顺序取数（`chart_rows` 缺省时回落 `rows` ⇒ 存量报告逐字节不变）：

| 图 | 数据源（优先 → 回落） | 列位契约 |
|---|---|---|
| `chartValuation` | `valuation.chart_rows` → `.rows` | 时点 \| PE \| PB \| 备注 |
| `chartCap` | `capacity.chart_rows` → `.rows` | 产品 \| 产能(数值) \| 利用率 % |
| `chartProd` | `production.chart_rows` → `.rows` | 产品 \| 产量 \| 销量 \| 产销率 % |
| `chartPrice` | `pricecost.chart_rows` → `.rows` | 期间/品种 \| 均价 \| 成本 \| 毛利 |
| `chartResDist` | `resource.rows`（只有这一份） | **列 1 与列 3 必须是数值** |
| `chartMix` | `bizmix.mix / income / margin` → `.rows` | 见 ② |

孪生键（**全部可选，缺省不显示** ⇒ 存量报告零影响）：

| 键 | 挂在哪 | 作用 |
|---|---|---|
| `capacity/production/pricecost/raw .chart_unit` | 图的 **y 轴名** | 只给图的轴名，与表格底部的 `unit_note` **分工**（后者可以是一整段话） |
| `capacity/production/pricecost/raw .chart_note` | 同模块的「**口径：…**」段 | 只与**图**有关的口径（图取的是**哪一期/哪一列**、为什么少一条系列）。与 `unit_note` **同时存在则两个都输出** |
| `valuation.head` / `valuation.section` | m28 的**表格表头** / **小节名** | `valuation.rows` 有两种口径（速览表 / PE-PB 序列）⇒ 表头不能再写死 |
| `valuation.chart_rows_note` | 图下方折叠块「**估值区间口径**」 | PE/PB 序列的取数口径与自证 |
| `sdbalance.bal_note` | 平衡表下方「**口径：…**」段 | 从 `bal_rows` 里挪出来的**定性**说明（2027 年平衡条件、全球口径参照） |

⚠️ **写了不显示的两个高发原因**（2026-10-16 都实际发生过）：
① 键名拼错 / 渲染器**根本没读这个键** —— 新加字段前先 `grep` 渲染器确认调用点；
② 漏跑 `_norm_bold.py <code> --go` ⇒ 库里残留字面 `**`（判据：库里 31 个模块的 `**` 计数必须是 **0**）。

**② `bizmix` 有**两套列口径**，绝不能再按列号取：**

| 口径 | 列 | 毛利率在第几列 |
|---|---|---|
| 新（603227 / 000762）7 列 | 产品 \| 收入(元) \| **毛利率** \| 收入(万元) \| 收入占比 \| 毛利占比 \| 排名变化 | **列 2** |
| 旧（603977 等）5 列 | 板块 \| 收入(亿元) \| 收入占比 \| **毛利率** \| 定位 | **列 3** |

⇒ 新口径的 seed 本就备好 `mix / income / margin`（`income` **单位＝万元**）⇒ 渲染器直接吃；
旧口径无这三个字段 ⇒ 回落列号。⚠️ m11 的 `chartMix` 最终会被 `mkmod11_ring.py` 的双环覆盖，
所以这条的真正风险是「重跑了 build 又忘了跑 ring」。

**③ ★★ 建图与挂槽的判据必须逐字一致。** `chart_opts()` 决定「建不建这张图」，
模块渲染器（如 `m15`）决定「挂不挂这个槽」—— 两处判据分居两个代码段，**改一处忘另一处就出孤儿图**
（图有数据、页面不显示、且不报错）。2026-10-16 实踩：`chart_opts` 已放宽成
`numeric_rows(rows, need=1)`，而 `m15` 仍写 `numeric_rows(rows)`（要求三列齐备）⇒
000762 的 `chartPrice` 成了孤儿。**改这类判据前先 grep 所有调用点。**

**③b ★★ 闸要卡「图真正用到的那几列」，不是任意列。** `numeric_rows(rows, idx=…)` 的 `idx` 默认是
`(1,2,3)`，但每张图只吃其中几列 ⇒ 卡错列会**放行一张空图**。实踩（2026-10-16 恒邦 002237）：
`chartCap` 只画**列 1（产能柱）+ 列 2（利用率线）**，而该表把利用率放在**列 3** ⇒
`need=1` 判「任意列」时列 3 的 `68.31%` 让它通过，图照建、列 1/列 2 全 `None` ⇒ 又一张「只有坐标轴」的图。
**正解**：`numeric_rows(cp, idx=(1, 2), need=1)` —— 按该图的列契约写 `idx`。
同一次改动顺带修好了 **600459 贵研铂业**（它线上那张 `chartCap` 本来就是 `[None×8]`）。

**④ 列 1 / 列 3 必须是**纯数值**。** `numcol()` 只剥 `%` `,` `x` `X`，**不剥 `**`** ⇒
写 `"**3,700**"` 会静默变 `None`（图上断点）；写 `None` 又会被渲染成红色 `[MISSING]`。
⇒ 要好看就写 `"3,700"`（能剥逗号）；确实没有的数写 `"—"` 或说明文字（图该断就断，**别用 `None`**）。

**⑤ ★★★ `report_build_v31.py` 会丢掉 `chart_eps`。** 它由 `apply_eps_to_11.py` 单独挂上去，
**不在 `chart_opts()` 的产出里** ⇒ 重跑 build 后必须**再跑一次 `apply_eps_to_11.py --go <code>`**
（该脚本有幂等保护，重复跑只会 upsert 图行）。同理 `mkmod11_ring.py` 的双环也一样。
**收尾必须 `sync_seed_full.py <code> --go`**，否则库与 seed 脱钩。

## 10. ⚠️⚠️ 撤销的方案：「表图去重」—— 用户试用后要求退回（2026-10-15 中午）


**状态：已完整回滚，线上与本地均已复原。** 用户看到效果后说「不改了退回来」。

### ★★ 本项目最贵的一条教训（比方案本身重要）

**线上研报的模块 HTML 早就与 `data_v31_*.json` 脱钩了。**

实测：600456 的线上备份有 **43 张表**，而用 `report_build_v31.py` 从 data seed 重建只有 **21 张**。
原因是 m3（`mkmod3_std.py`）、m22（`mkchain_std.py`）等模块经后处理脚本改写，另有大量手工版式调整
—— **这些成果只存在于库里，不在 seed 里**。

⇒ **两条硬纪律：**

1. **要撤销线上改动，只能用 `push_reports_v31.py` 自动生成的备份回滚**，
   绝不能「改回渲染器 + 重建 seed + 推库」—— 那会把后处理成果**全部抹掉**，
   那是比原改动严重得多的破坏。
2. 备份在 **`build/backup/report_<code>_pre_v31_<时间戳>.json`**，
   结构 = `wb_reports` / `wb_report_mods`（★ **键名带 `wb_` 前缀，不是 `mods`**）/
   `wb_report_charts`。**每次写库前先确认这份备份在**，它是唯一的回滚凭据。

回滚工具：`build/rollback_from_backup.py`
（`--list` 列备份 / `--all` 全回滚 / `<code>` 单份），逐模块 `PATCH html` 并回读逐字核对。

### 方案本身（存档，供日后若重启时参考）

用户当时的原话是「既有表格又有图表的只显示图表，表格全部去掉」，
配 000762 m14 的截图（28 行月度价格表 + 同一份数据的折线图）。

逐格审计全库 98 组表图配对后分四类：

| 类别 | 组数 | 处置 |
|---|---|---|
| 表格 100% 被图覆盖 | 27 | 直接删表 |
| 主体重复 + 少量图外文字 | 8 | 删表，文字转图下注释（`<p class="chnote">`） |
| 图与表**不同数据源** | 32 | 保留（m9 图取 `industry.size` 而表取 `rows`；m11 图只画营收而表有毛利率/PE/定位） |
| 同源但图外文字多 | 31 | 保留（m20 有「占比/毛利贡献」整列解释性文字） |

**第一原则：图只画得出数值，画不出文字列** —— 用户截图那张表的「备注：区间高点 67」
图里就没有，无脑删表 = 丢信息。

若日后重启，核心是 `table_dup_note(head, rows, max_note_ratio=0.34)` 的**三态返回**：
`''`=整表可删 / `<p class="chnote">`=可删+文字转注释 / `None`=**保留表格**；
且**必须配一份回归测试锁住判定值**（数值识别极易出错，见下）。

⚠️ **数值识别（`_cnum`）的三个坑，每个都真实发生过**：

1. 必须 `re.fullmatch` 不能取前缀 —— 否则「2025-01」读成 2025.0；
2. 年份/年月一律当标签（图里是字符串类目，「2021」曾整列误报）；
3. 容忍带单位（「4.27 万吨」「1,599 元/吨」），但**模糊量词开头不算数值**
   （「超 2,000 吨」「2,000+ 吨」）—— 判错方向就是删错表。

改动版存档在 `/tmp/rollback_keep/`（渲染器 + CSS + 审计/测试工具）。
⚠️ **`/tmp` 会被系统清理，重启前先拷进 `build/backup/`。**
